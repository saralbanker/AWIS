00The answer, stated first

What actually caused the AWIS documentation crisis

Every truth-preserving mechanism AWIS built — the STATE.md ledger, the archive, the indices, the frozen canon — depended on continuous human attention and had no failure mode. A forty-day dormancy broke that attention. When work resumed, reading the record had become more expensive and less trustworthy than re-deriving it from the code, so the project re-derived. Re-derivation appends rather than replaces, and nothing in the system could retire what it superseded, so every subsequent session multiplied the number of authorities instead of reducing them.

The crisis is not drift between documentation and code. It is the replacement of a maintained record by an accumulating one.

The rest of this report is the evidence for that sentence, and the corrections it forces on several intuitively appealing alternatives — including the hypothesis that GUI planning caused this.

01The architecture that originally existed

On 2026-07-02–03 AWIS was given a complete, deliberately-designed documentation architecture in essentially a single act. Commit 441f017 — the first commit in the repository, literally titled "canonical planning corpus + Implementation Knowledge Base as-is" — landed the whole thing at once. It had four layers, and they were coherent.

Layer 1 — the frozen canon

Fourteen root-level documents totalling roughly 700KB: OIP_CONSTITUTION.md, AWIS_ARCHITECTURE_FINALIZATION.md, AWIS_ARCHITECTURE_BLUEPRINT.md, AWIS_PRD.md, IMPLEMENTATION_MASTER_PLAN.md and its verification report. docs/README.md declares these IMMUTABLE and fixes a strict authority order in which conflicts resolve upward.

Layer 2 — the Implementation Knowledge Base

The docs/ tree, numbered 00-foundation through 07-indices. Its stated contract is unusually disciplined: "this tree partitions and cross-references them — it never restates them." It carries a deterministic five-step session loading protocol designed to keep a model's context under 8k tokens, and a contradiction protocol requiring a session to STOP and record rather than silently resolve.

Layer 3 — the milestone modules

One directory per milestone, M00–M18, each bound to a seven-file contract: README, IMPLEMENTATION_SPEC, AI_EXECUTION_CONTEXT, VALIDATION_CHECKLIST, HANDOFF, TRACEABILITY, DEPENDENCY_MAP. Modules are lazily materialised at milestone entry, with a recorded rationale: pre-writing a HANDOFF would "fabricate actuals." This is a genuinely sophisticated anti-drift design.

Layer 4 — the execution operating system

Added 2026-07-08 at M06: EEOS.md (bootstrap) and AWIS_EEOS.md (normative), with AWIS_ENGINEERING_ORGANIZATION.md defining four roles. A five-phase machine — A-INIT → B-BUILD → C-VERIFY → D-CLOSE → E-MERGE — with immutable Execution Cards, an independent verifier that never sees implementer reasoning, and one governing rule above all others:

EEOS Rule 1 — Ledger law

"No phase or card transition is real until it is written to STATE.md." docs/05-implementation/STATE.md is defined as the single source of live execution state.

02Was that architecture sufficient?

It was sufficient to produce excellent work, and insufficient to survive its own author's absence. Both halves are demonstrable.

Under this architecture, M00–M14 executed with a rigour that is rare. Every one of those fifteen modules carries all seven contract files. Every card maps to exactly one commit. Verification was independent and the verifier's reports were not sanitised — STATE.md contains an entry where an independent verifier explicitly refused to accept an implementer's self-trace as adjudication, and re-measured the diffs. Nine milestones carry git tags. That is a functioning system.

But the architecture contained no mechanism that enforced itself. Consider what it declared, and what actually happened to each declaration across eighteen milestones:

Verified

docs/00-foundation, 01-vision, 02-architecture, 03-product, 06-reference and 07-indices each have exactly one commit in the entire history of the project — 441f017, 2026-07-03. Eighteen milestones ran on top of a foundation that was never touched again. T4 T2

Answer: the original architecture was sufficient as a specification and insufficient as a system. It described a maintained record without building anything that would notice when maintenance stopped.

04Where fragmentation began

Truth fragmentation has a precise mechanical origin, and it is not a document. It is the decision to store the single source of truth inside a medium that forks.

STATE.md is defined as the live execution state. It lives at docs/05-implementation/STATE.md — inside git, on a branch. EEOS then instructed milestones to stack branch-on-branch (m10 → m11 → … → m17) while E-MERGE waited on a single human. The predictable consequence is measurable today:

Four simultaneously-live, mutually inconsistent versions of a document whose defining property is singularity. And the divergence is not merely between branches — it is between main and main's own history:

Finding — the ledger contradicts its own branch

On main, STATE.md records M10, M11, M12, M13 and M14 as PHASE: E-MERGE (blocked on founder), and DONE-MILESTONES ends at M09. main's git log contains f6aa755 "M10-M14", a merge commit by the founder dated 2026-08-20, and the code for all five milestones is present in the tree. The ledger has been false about its own branch for three weeks. T2 T4

This matters more than it first appears, because EEOS anticipated exactly this state and specified the response. Its phase-resume table has a row reading "ledger contradicts repo → STOP — Fable wake; never 'fix' STATE to match a guess." The system's own instruction for its current condition is to halt. Nobody halted; the work simply moved elsewhere.

05What caused fragmentation

The mechanism has three stages, and each is independently evidenced.

Stage one — a gate that could not be bypassed and was not attended

EEOS rule 6: "Merges are human-only." There is no timeout, no fallback authority, and no bound on queue depth. By 2026-07-11, six consecutive milestones were queued behind one person. The queue did not fail loudly; it simply grew, and the branches stacked on each other so that nothing could merge independently.

Stage two — dormancy destroyed the cheapness of reading

Forty days later, the ledger's accuracy was unknown, M17 was mid-card with a dead dispatch, and six merges were outstanding. EEOS has a resume protocol for precisely this. It was not used. The first artifact produced on resumption day was an audit — 1b98ee2, "repository truth audit — independent re-verification of M15/M16/M17", 420 lines.

Stage three — re-derivation became self-reproducing

Within the same day, on pushed branches, the project produced:

2026-08-20  1b98ee2  audit: repository truth audit
2026-08-20  6dccb89  audit: record live CI evidence from this branch's own push
2026-08-20  f348b28  audit: independent audit of the Repository Truth Audit
2026-08-20  8c7ac6a  audit: final architecture arbitration over both repository audits
2026-08-20  8f88458  decision: final decision review over all three prior reviews
2026-08-20  c672186  verify: final independent verification of the M18 A-INIT path

A four-level recursive adjudication stack, produced in one day, on three separate branches, none of which was ever merged into main or engine-hardening. Those 1,700 lines of adjudication are invisible to every subsequent session. They created a new directory, docs/06-audits/ — colliding with docs/06-reference/ on main, so the docs/ tree's own numbering now depends on which branch you are standing on.

This is the moment the project's epistemology changed. Before it, truth was read from a maintained ledger. After it, truth was re-derived from code. Re-derivation is sound as an act and catastrophic as a habit, for one structural reason: it produces a new document rather than correcting the old one. And because nothing could retire the old one, the population of authorities grew monotonically from that day forward — twenty root-level verdict documents, four numbered docs/ folders, five files named FINAL_VERDICT.md.

The pattern, self-observed

DOCUMENTATION_DIVERGENCE_REPORT.md records that the single most important fact in the repository — that the GUI and API were never committed — was independently rediscovered on 2026-08-30, 09-01, 09-03, and twice on 09-05, "each writing as though this were a fresh discovery." Between the first and last rediscovery, zero commits added any of those paths to git. The finding was documented five times and acted on zero times. That ratio is the crisis. T4

06The GUI planning question

Verdict: contributor and symptom. Not root cause, and not unrelated.

Why it cannot be the root cause

Chronology settles this. GUI planning's own README dates its evidence base to 2026-08-30. By that date:

  • The last write to STATE.md was nine days old (2026-08-21).
  • EEOS had already been abandoned for four days — the B- series began 2026-08-26 with zero ledger rows.
  • The recursive-audit pattern was already ten days old.
  • main and engine-hardening had already diverged irreconcilably.

Every structural failure attributed to GUI planning predates it. It did not abandon the milestone system; it arrived after the milestone system had stopped.

Why it is not innocent

It is the largest single block of duplicate authority in the repository: 38 documents, flat, no subdirectories, zero commits. It contains five competing terminal answers — FINAL_VERDICT.md, FINAL_RECOMMENDATION.md, GUI_BETA_FINAL_RECOMMENDATION.md, GUI_PHASE1_FINAL_RECOMMENDATION.md, STARTLINE_FINAL_VERDICT.md — each offered as the thing to read "if you only have two minutes." Its own README carries a "Standing conclusion" section whose first words are that the standing conclusion is superseded.

It also drove scope past the canonical boundary. AWIS_PRD.md — single commit, 2026-07-02, never amended — scopes the web dashboard as V3 work (line 116), authentication as V3 (NG-4), and a web-accessible status page as V2 (§17). The GUI and HTTP API were built into a V1 baseline anyway. The PRD was never touched.

The correction this investigation must make

The intuitive reading — that GUI planning was sloppy where engine documentation was rigorous — does not survive measurement. docs/09-gui-planning/README.md is the best-indexed document in the repository. It dates every one of its six passes, states explicitly what each supersedes and what it does not, distinguishes "new investigation" from "decomposition only," and flags its own limits — including that the entire plan is evaluated against a branch main is 60 commits behind. It even records a factual error it made and retracted.

Compare that with the engine foundation's docs/06-reference/README.md, which states: "A missing TDS here means its milestone has not executed." The directory is empty. Six of seven TDS exist elsewhere. That sentence has been false since the day after it was written.

Conclusion

GUI planning is the first large body of work produced after governance stopped. It therefore shows what AWIS documentation looks like without governance — which is sedimentary, verbose, redundant, and individually more honest about its own authority than the governed foundation ever was. It is the symptom rendered at scale, plus a genuine contributor of duplicate-authority mass and out-of-scope implementation.

07Latent defects in the original foundation

Yes — three, and one of them is a false state oracle that has been lying since day one.

Defect A — the 06-reference path mapping

docs/06-reference/README.md declares a "recorded, not silent" path mapping: IMP §12 names paths like docs/EVENTLOG_FORMAT.md; "in this repository they resolve to docs/06-reference/<NAME>.md." It then tabulates TDS-01 through TDS-07 as living there.

Not one of them does. All six repo-side TDS files were created at docs/ root — three of them by M01 on 2026-07-03, the same day the mapping was written. No milestone module anywhere references the 06-reference path; every one of them cites docs/<NAME>.md directly. The contradiction was never recorded as a CONTRA, despite the foundation's own contradiction protocol requiring exactly that.

This produces two compounding failures. The first: docs/README.md's deterministic loading protocol, step 3, instructs every session to "load only the TDS files in 06-reference/ that the execution context names." Following the documented protocol yields an empty directory. The second is worse — the same README states a falsifiable claim about project state:

A false oracle, load-bearing since 2026-07-03

"Empty until the creating milestone runs. A missing TDS here means its milestone has not executed."

The directory contains only its own README. By its own rule, M01, M11, M12 and M14 have not executed. All four executed, were independently verified, and are merged into main. T2

Defect B — the archive was declared but never wired to an obligation

Two documents establish archive/ as the destination for superseded material. Nothing states who archives, when, or what checks it. Across 387 documents and eighteen milestones it was used zero times. Its sole occupant is its own README, which describes a superseded blueprint that it explicitly notes is retained at the repository root rather than archived — the retirement mechanism documenting its own non-use in its only entry.

Defect C — write-once indices carrying a protocol dependency

EEOS's "Lookup discipline" section makes docs/07-indices/cross-reference-index.md mandatory: "A question about the frozen design → cross-reference-index → one coordinate → load only that section. Browsing canonical documents 'for context' is a protocol violation." That index has one commit, dated M00. It still describes TDS-07 as "M14 day 1" future work and stops at migration 0005; migration 0006 shipped in M17. A protocol made lookup mandatory through an artifact nothing obliged anyone to update.

None of these three caused the crisis. All three establish the same property: the foundation specified behaviour it could not detect the absence of. That property is the crisis's precondition.

10Earliest point of divergence

The question has three honest answers at three different depths, and collapsing them loses information.

Latent divergence — 2026-07-03, commits 441f017 / aef89bf

The foundation was authored write-once; the archive was declared without an obligation; the indices were made mandatory without a maintainer; and the TDS path mapping was contradicted by the very first milestone that exercised it, on the same day, without a CONTRA being raised. Nothing broke. But from this moment the system had no capacity for self-repair.

Active divergence — 2026-07-10

The first recorded instance of the ledger being false about the repository: STATE.md said M09 was blocked at E-MERGE while main already contained its squash-merge. The significant event is not the contradiction — it is the repair. It was found and fixed by a manual reconciliation pass, which established that ledger–repository consistency was maintained by attention rather than by mechanism. The same failure recurred six weeks later and was never repaired, because the thing that caught it the first time was a person noticing.

Point of no return — 2026-08-20

Three irreversible things happened on one day: five milestones were merged without a ledger write, making the ledger permanently false; the recursive-audit genre was born and immediately reached four levels; and the audit output was pushed to branches that were never merged, so the re-derivation was itself lost. After this date, no document in the repository accurately describes the repository, and re-derivation became the only reliable method — which guaranteed the document count would grow without bound.

If forced to name one: 2026-07-10, the unrepaired-by-mechanism repair. That is where the project learned, without noticing, that its truth system ran on attention.

11Can any model work here today?

Four capabilities, assessed against the repository as it exists. The demonstration that settles all four is worth showing first, because it is the cleanest Tier-1 fact in this investigation.

The version-golden demonstration

main fixed toolchain-pinned test goldens in d5ac004 (2026-08-20), whose commit message records it was "found by the first CI run in the project's history." That fix never reached the branch holding all the work:

$ git merge-base --is-ancestor d5ac004 engine-hardening   →  NO

$ git show engine-hardening:cmd/awis/testdata/golden/version.txt
awis version 0.1.0-dev  go go1.26.5          # committed: pinned to one patch release

$ git show main:cmd/awis/testdata/golden/version.txt
awis version 0.1.0-dev  go <go-version>      # committed: normalised

$ cat cmd/awis/testdata/golden/version.txt    # the working tree, right now
awis version 0.1.0-dev  go <go-version>

$ git status --porcelain cmd/awis/
 M cmd/awis/main_test.go
 M cmd/awis/testdata/golden/version.txt        # the fix is UNCOMMITTED

$ go test ./cmd/awis/ -run TestVersion         # this machine, go1.26.5
ok  github.com/awis/awis/cmd/awis  0.003s

The test passes here. It passes because this machine runs the exact Go patch release the golden was pinned to, and because the working directory carries an uncommitted fix that exists on no branch. CI resolves 1.26.x to the newest patch. A clean clone of engine-hardening @ 8a87f70 — the commit every audit in this repository evaluates — fails.

What this proves

The repository's health is a property of one uncommitted working directory, not of anything in version control. Nine tracked files carry uncommitted modifications, two of which (cmd/awis/main.go, cmd/awis/start.go) depend on internal/buildinfo, a package that has never been committed. T1 T2

Understanding by any model

Only by ignoring the documented path

The documented cold-start route is CLAUDE.md → EEOS.md S1 → STATE.md, which is 33 commits, one abandoned protocol and four docs-folders out of date. An accurate account of the project does exist — TRUTH_CLOSURE.md — but it is untracked, referenced by nothing, and named in no entry point. It is found by listing the directory, not by following any route the repository provides.

Continuation by any model

No

EEOS's own phase-resume table specifies the response to the current state: "ledger contradicts repo → STOP." A protocol-compliant model halts on arrival. A non-compliant one proceeds against a ledger asserting that M10–M14 await merge (they are merged), that M15/M16 await merge (they are not on main at all), and that the live milestone is M17 C-VERIFY — while the actual work is an unledgered defect program, a GUI, and an HTTP API.

Reconstruction by any model

No

Reconstruction requires the artifact to be in the artifact store. An entire product surface — internal/api, cmd/awis-server, web/, internal/buildinfo — has zero commits on any branch in the project's entire history, alongside 59 untracked docs-tree files and ~20 root reports. A clone reconstructs a smaller, different project that cannot pass its own CI.

Safe execution by any model

No

Two independently sufficient reasons. First, the branch holding all the work cannot pass its own CI from a clean checkout, so "the gates are green" — the premise under every confidence claim in the corpus — is unverifiable by anyone but this machine. Second, there is no live ledger to write to: any work performed is unrecorded by construction, which is the exact condition that produced this state.

One qualification matters, and it cuts the other way: the engine itself is in good condition. Independent spot-checks in this investigation confirmed the architecture matches its documentation, the milestone execution records are accurate against their commits, and the hardening program's defect work is real. The failure being diagnosed is a failure of the record, not of the software.

12Characteristics the final architecture must possess

Stated as properties the evidence shows are required — not as a plan, a sequence, or a disposition of existing files.

  1. Branch-independent live state. The single record of what phase the project is in must not live in a medium that forks. RC-1 is the whole of this.
  2. Every governance mechanism must have an enforcement surface that fails loudly. A rule checked by attention is not a rule. A mechanism used zero times across 387 documents was never a mechanism — it was a sentence.
  3. Truth must be reconstructible from the artifact store alone. If a claim's evidence is untracked, the claim is not evidence. The corpus currently cites untracked files from untracked files.
  4. Frozen documents need a defined amendment path. Immutability without an amendment procedure does not preserve the canon; it makes the canon irrelevant the first time reality moves, and the movement then goes unrecorded.
  5. Exactly one terminal answer per question, at a stable address. Superseding must replace at the address. Appending beside it is what produced five FINAL_VERDICT.md files, two of which disagree.
  6. Documents must declare their own expiry conditions. Every high-value document here was true when written and false within days. The commit, branch and toolchain a claim was true against must travel with the claim.
  7. A resumption protocol cheaper than re-derivation. This is the load-bearing property. When reading costs more than re-deriving, sessions will re-derive; re-derivation is not idempotent; and the document count grows without bound. Everything else in this list is downstream of this one.
  8. Reachability as an invariant. Every authoritative document must be reachable from the single entry point, and unreachable documents must be non-authoritative by definition — so that an orphan like TRUTH_CLOSURE.md is a detectable error rather than a silent one.
  9. A governed identifier namespace with one registry. Seven ad-hoc defect schemes is what "no registry" looks like after six weeks.
  10. No unbounded serialization behind a single human. Either the gate carries a timeout and a fallback authority, or it carries an explicit queue-depth limit that halts production when exceeded. Six queued milestones must be a loud failure, not a quiet backlog.

14Should the milestone framework be canonical?

Its artifact discipline: yes, decisively. Its state and gating mechanics: no — those are what produced the crisis.

The evidence for the first half is unambiguous. M00–M14 is the highest-integrity output in this repository by a wide margin: fifteen modules at 7/7 contract compliance, one commit per card, independent verification that was permitted to fail and did, nine git tags, and a ledger detailed enough to record its own defects. Nothing produced after the framework stopped approaches it.

But three of its mechanics are load-bearing in the failure, and they are not incidental to the design — they are the design:

  • Branch-resident single state. Rule 1 makes STATE.md the only real record of phase; rule 4 puts engineering state in git branches. Together these guarantee that the single source of truth forks whenever the work does. T2
  • An unbounded human merge gate. Rule 6 makes merges human-only with no timeout and no fallback. Combined with stacked branches, one unavailable person halts everything while the queue grows silently. T4
  • No resumption path priced below re-derivation. The phase-resume table exists and is well-designed, but reading it requires trusting a ledger whose accuracy after dormancy is exactly what is in question. It was not used once on resumption day. T4

Adopting the framework wholesale would reproduce the failure, and would do so at the same point: the first time one person is unavailable for more than a few weeks. The framework is the right model for how work is recorded — cards, sha-linked execution records, independent verification, honest ledger narrative — and the wrong model for where live state lives and who is allowed to advance it.

—Closing

Three hypotheses in the brief are refuted by the evidence and should not survive this report. GUI planning is not the root cause — it postdates the collapse of the governance system by nine days, and its index is more honest about its own authority than the foundation's. The original documentation architecture is not simply sound — it carried a false state oracle from its second day and three mechanisms it could not detect the absence of. And documentation drift is not the diagnosis — drift implies two things moving apart, whereas what happened here is that one of them stopped being written and was replaced by an accumulating pile of independent re-derivations, each locally accurate and collectively unusable.

What remains is a project whose software is in good condition and whose record of itself is not, held together by a single uncommitted working directory. The engine milestone framework was the best thing this project built. Its failure mode — a truth system that ran on attention, with no mechanism that noticed when attention stopped — is the single thing that must not be carried forward.
